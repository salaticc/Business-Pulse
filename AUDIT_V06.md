# Аудит и заранее заданный протокол v0.6

11.11.2026. Продолжение существующей v0.5, без замены прогнозирования,
Telegram-интеграции, API или новых инфраструктурных зависимостей.

## Аудит

Изучены model/data/evaluation/pipeline, notifications, CLI, тесты,
FORECAST_CONTRACT и отчёты v0.5. В исходной системе:

- признаки используют прошлое; прогнозная модель выбирается по CV;
- уведомление в старом backtest — shortfall выше 90-го процентиля
  validation И относительное отклонение >=25%; это эвристика;
- относительное отклонение использует clip(lower=1), что искажает долю
  для прогнозов между 0 и 1; в новом модуле знаменатель будет точным;
- checks data.py проверяют значения и сетку дат, но не время поступления;
- нет ground truth инцидентов, уровней серьёзности, стоимостной оценки;
- Telegram-дедупликация только по дате: не по потоку/эпизоду;
- load_alerts читает строки CSV, полагаясь на предварительную фильтрацию
  pipeline; это не универсальный фильтр всего журнала событий;
- actuals агрегированного файла не доказывают historical as-of availability;
- раскрытый TEST v0.4 не является новым независимым подтверждением.

Старые интерфейсы сохраняются. Модуль v0.6 не импортирует транспорт
notifications и не передаёт свой журнал старому scripts.notify.

## Решения до получения результатов

1. Детерминированные правила относительного И абсолютного shortfall,
   только по завершённому дню. Некорректные/неполные/устаревшие данные
   порождают отдельное событие качества; business warning блокируется.
2. Явные времена закрытия, полноты, формирования прогноза, открытия,
   снимка факта и обновления источника. Нельзя доказать их по одному CSV
   выручки; они обязательны в новом интерфейсе наблюдений.
3. Локальное состояние по stream + типу события, последовательные
   эпизоды, напоминания не чаще cooldown, эскалация при росте серьёзности,
   идемпотентность повторного снимка. Отправки в сеть нет.
4. Новая синтетика: 420 дней, 240 train / 90 validation / 90 test,
   seed=20261111. Генератор вмешательств создаёт метки независимо от
   порогов и остатка прогноза. Есть обычная волатильность без инцидента,
   инциденты разной длительности/тяжести и искусственные ошибки данных.
5. Прогноз: уже выбранная в v0.5 медиана t−7/14/21/28; алгоритм фиксирован.
   Если нужные исторические итоги недоступны на момент прогноза,
   прогноз не формируется. Обучение нового алгоритма не требуется.
6. Сетка до эксперимента: относительные 15/25/35/45%, абсолютные
   100/250/500 единиц выручки. Cooldown=7 дней, freshness=24 часа,
   high=40%, critical=65%. Разные политики получают отдельное состояние.
7. Цена ложного business warning = 3 условные единицы; пропуска целого
   инцидента mild/major/critical = 15/45/150, умноженные на заранее
   сгенерированный вес конкретного эпизода 0.75/1/1.25. Это назначенные учебные
   предпочтения, не оценка финансового ущерба. Их можно менять в config.
8. Выбор только по validation: минимум общей стоимости, затем меньше
   ложных предупреждений, затем порядок политик. После выбора состояние
   переносится из validation в test. Все TEST-пороги не сравниваются.
9. Confusion matrices по дневным решениям до/после подавления; отдельные
   TP/FN/Recall по целым инцидентам. TN по инцидентам не определяем.
   Заблокированный из-за данных инцидент не исключается из FN/стоимости.

## Ограничения модели затрат

Своевременное предупреждение в любой размеченный день инцидента даёт
ему статус обнаруженного; задержка внутри эпизода сообщается, но не
штрафуется. Цена проверки истинных сигналов и предотвращённый ущерб не
моделируются. Дни продолжающегося инцидента после подавления могут быть
FN дневной матрицы, хотя сам инцидент уже обнаружен. Поэтому стоимостная
оценка не вычисляется умножением дневных FN на цену целого инцидента.

Состояние сбрасывает эпизод при нормализации/блокировке данных/пропуске
календарной даты. Повторный снимок того же дня не выдаёт новое сообщение;
изменённый снимок требует явного переигрывания с чистым состоянием.
Это конечный локальный последовательный evaluator, не многопроцессный сервис.
