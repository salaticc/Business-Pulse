**Учебный MVP для портфолио:** прогноз дневной выручки интернет-магазина, сравнение с простым базовым методом и сигнал о резких отклонениях. В перспективе — модуль ранних предупреждений мобильного Business Pulse.

## Зачем это бизнесу

Владелец ежедневно получает много цифр и не всегда замечает резкое отклонение с учётом дня недели. Система предлагает: ожидаемый диапазон → факт → сигнал → что проверить. Она НЕ знает причин автоматически и НЕ доказывает потери прибыли.

## Данные

- **Реальные данные:** Daqing Chen (2015), *Online Retail*, UCI Machine Learning Repository, https://doi.org/10.24432/C5BW33, лицензия CC BY 4.0. Транзакции UK-магазина, 01.12.2010–09.12.2011, 541 909 строк в исходном наборе, 22,6 MB XLSX. Это не российские данные 2026 года.
- **Демо:** `data/demo/daily_sales.csv` — СИНТЕТИЧЕСКИЕ данные с искусственно добавленными провалами для проверки работоспособности.
- **Обозначение выручки:** сумма положительных строк заказа (`Quantity * UnitPrice`), отменённые заказы и некорректные строки исключаем. Это не чистая выручка, не прибыль и не экономический ущерб.
- **Страны:** для UCI по умолчанию `United Kingdom` (это НЕ филиал). Для другой страны: `--country Germany`.
- Отсутствующие даты теперь вызывают ошибку. Только явное `--missing-days zero`
  разрешает исследовательское заполнение нулями; даты и допущение попадут
  в отчёт. Даже непрерывная дневная сетка не подтверждает полноту выгрузки.
  CSV неизвестного происхождения не помечается синтетикой автоматически.

Повторный запуск воспроизводит расчёт, но не создаёт новый независимый тест.

### Протокол v0.5

Прогноз формируется после закрытия предыдущего торгового дня и подтверждения
полноты загрузки, до открытия дня t. Само время 18:00 или начало новой
даты этого не гарантирует. Лаги относятся к календарным дням: для закрытых
дат также требуется подтверждение календаря.
Разрешены календарь и факты до t−1. Текущие revenue/orders/aov не являются
признаками. Этот контракт предполагает, что вчерашняя выгрузка полная;
без подтверждения источником эксперимент не доказывает пригодность в работе.
В v0.5 нет оперативной проверки закрытия/полноты и исторических времён
поступления данных: это допущение backtest, а не реализованный допуск к прогнозу.

Сравниваются `last_same_weekday` (t−7), `four_week_median`
(медиана t−7/14/21/28) и `gradient_boosting` (исходный HGB, seed=42,
early_stopping=False, без подбора гиперпараметров). В каждом окне ML
обучается на всех более ранних feature-ready днях. Веса внутри окна
фиксированы, а лаги обновляются из наблюдённых фактов. После выбора ML
один раз переобучается на всей истории до TEST для итогового сравнения
трёх методов; выбор уже зафиксирован. TEST не используется для настройки.

По умолчанию: 28 дней прогрева, 3 непересекающихся окна validation по
28 дней, последние 60 дней TEST, минимум 60 обучающих строк после прогрева.
На демо из 280 дней:

| Окно | Конец обучения | Validation | Обучающих строк |
|---|---|---|---:|
| 1 | 16.05.2025 | 17.05–13.06.2025 | 108 |
| 2 | 13.06.2025 | 14.06–11.07.2025 | 136 |
| 3 | 11.07.2025 | 12.07–08.08.2025 | 164 |
| Финальный refit | 08.08.2025 | TEST 09.08–07.10.2025 | 192 |

Начало feature-ready обучения — 29.01.2025. Validation кратна неделе,
expanding train сохраняет больше наблюдений, чем фиксированное окно.
Цена — лишь три близких во времени окна; годовую устойчивость и
статистическую значимость разницы они не устанавливают. Минимальная
длина при этих параметрах — 232 календарных дня, иначе явная ошибка.
Параметры можно задать заранее: `--folds 3 --validation-days 28
--test-days 60 --min-train-days 60`. Не менять их по результатам TEST.

Метрики без округления до выбора: MAE = mean(|y−p|),
RMSE = sqrt(mean((y−p)²)), WAPE = 100·sum(|y−p|)/sum(|y|).
При нулевом знаменателе WAPE — `null`, не 0; полностью нулевая CV
останавливает выбор. Выбор — минимальный **pooled OOF WAPE** всех
validation-дней. Это не среднее WAPE окон: объёмы продаж различаются.
При точном равенстве предпочтителен более ранний метод в списке выше.
Для каждой метрики отдельно сохраняются mean/std(ddof=0)/min/max по
окнам и число окон с определённой метрикой. Разброс не является
доверительным интервалом; наблюдения и окна зависимы.

**Честность holdout:** метрики последних 60 дней демо уже показаны в
v0.4. Новый алгоритм выбора не получает их, что проверяется тестами с
изменением будущих значений, но это не ранее невиданный эксперимент.
Следующее подтверждение качества требует новых данных после фиксации
протокола. Показатели здесь относятся к синтетике, не к реальному UCI.

## Как устроен прежний pipeline / compare_models (v0.4, сохранены)

- Признаки: день недели, месяц, календарный день, продажи за 1/7/14/21/28 дней ранее, скользящие средняя и разброс, рассчитанные **только из прошлого**.
- Baseline: медиана продаж за те же дни недели предыдущих четырёх недель.
- ML: `HistGradientBoostingRegressor` из scikit-learn.
- Время прежних команд: TRAIN → VALIDATION (35 дней) → TEST (60 дней).
  На VALIDATION выбираем метод; затем сравниваем на TEST. Для этапа v0.5
  используйте `scripts.evaluate` с несколькими окнами, как описано выше.
- Указанные метрики относятся к **историческому backtest с однодневным горизонтом** (в каждый день мы уже знаем вчерашние продажи). Это не прогноз на 60 дней вперёд.
- Алерт: отрицательное отклонение больше порога на основании VALIDATION **и** не менее 25% относительно прогноза. Это эвристика, а не статистически калиброванная вероятность инцидента.

## Ограничения и честность

- В UCI нет причин провалов (остатков, рекламы, графика работы, инцидентов сервиса).
- Нет разметки настоящих проблем: нельзя честно заявлять precision/recall детектора аномалий.
- Часть нестандартных заказов может быть оптовой; средняя выручка волатильна.
- ML **не гарантирует** превосходство над baseline. В этом случае продукт выбирает baseline, а отрицательный результат объясняется.
- Продакшену нужны безопасное подключение к источникам, контроль задержек и пропусков загрузки, обработка закрытых дней, согласование уведомлений и мониторинг дрейфа.

   ```powershell

   ```
