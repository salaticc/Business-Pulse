# G-Analytics Business Pulse — учебный маршрут с результатами

Принцип: сначала понять задачу и подтвердить результат, затем добавлять инструменты. Этот файл — план, а не список технологий, которые нужно выучить до старта.

## Этап 0. Разобраться с существующим кодом (1–3 учебные сессии)

- [ ] Запустить демо и четыре исходных теста.
- [ ] Объяснить каждый файл `src/`, что поступает на вход и что возвращается.
- [ ] Самостоятельно ответить на вопросы `TALENT_TEST.md` до чтения готовых алертов.
- [ ] Назвать минимум три ограничения данных UCI.

**Результат:** можешь своими словами нарисовать поток данных и объяснить происхождение прогноза.

## Этап 1. Анализ и статистическая дисциплина (3–5 сессий)

- [ ] Загрузить реальный UCI Online Retail и сделать EDA: выручка по дням, число заказов, средний чек, пропуски, возвраты.
- [ ] Разобраться, чем `revenue` в MVP отличается от бухгалтерской выручки/прибыли.
- [ ] Проверить гипотезу: достаточно ли объясняет продажи день недели.
- [ ] Сделать разбор двух предупреждений и альтернативных гипотез.

**Навыки:** Pandas, EDA, визуализация, метрики бизнеса, проверки качества данных.

## Этап 2. Настоящий ML-эксперимент (4–6 сессий)

- [ ] Без подсказки объяснить `lag_7`, rolling features и утечку в будущем.
- [ ] Сравнить baseline и Gradient Boosting на валидации, оценить тест только после выбора.
- [ ] Изменить ОДИН признак и записать гипотезу до эксперимента.
- [ ] Провести 3–4 последовательных временных сплита (rolling-origin CV) и оценить устойчивость вывода.
- [ ] Оценивать точность прогноза отдельно от полезности алертов (для второго нужны метки инцидентов).

**Навыки:** scikit-learn, регрессия, ансамбли, feature engineering, backtesting, научная честность.

## Этап 3. Telegram и продуктовая логика (2–4 сессии)

- [ ] Посмотреть `python -m scripts.notify` (только preview; не отправляет сообщения).
- [ ] Сверить существующий бот и его структуру с адаптером `src/notifications.py`.
- [ ] Добавить бизнес-правила: не присылать повторно одну дату, учитывать выходные, отсутствующие данные.
- [ ] Проверить, понятен ли текст алерта владельцу; спросить, какое действие он предпринял бы.
- [ ] Тестировать настоящую доставку только с разрешения получателя; бот-токен хранить в окружении и никогда не публиковать.

**Навыки:** API, Python-модули, интеграции, exceptions, тестирование, безопасность секретов.

## Этап 4. Инженерия и деплой (3–6 сессий)

- [ ] Перенести агрегированную таблицу продаж в SQLite, потом при необходимости PostgreSQL.
- [ ] Описать ежедневное расписание: загрузка → проверка полноты → прогноз → правила → уведомление.
- [ ] Настроить логирование, контроль отказов и типизацию важных интерфейсов.
- [ ] Добавить GitHub Actions CI для тестов, Docker — только когда приложение станет воспроизводимым без контейнера.
- [ ] Задокументировать результаты, ограничения, запуск и пару бизнес-алертов для портфолио.

**Навыки:** SQL, ETL, Git, CI/CD, Docker, сервисный подход.

## Этап 5. Optuna, API, мобильная панель — только после этапов 0–4

- [ ] Сформулировать улучшение метрики, оправдывающее тюнинг.
- [ ] Оптимизировать гиперпараметры только на временной валидации.
- [ ] Сделать FastAPI endpoint для KPI и алертов, потом PWA/мобильный интерфейс.
- [ ] Согласовать и проверить реальные бизнес-данные и разрешения на использование.

**Намеренно не сейчас:** PyTorch, нейросети, Kubernetes, real-time streaming, «умные» причинные объяснения без данных.

## Мини-тест твоего мышления

На каждом этапе фиксируй: гипотеза → действие → фактический результат → что узнал. Оцени интерес (1–5), концентрацию (1–5), желание продолжить (1–5). Это диагностика предпочтений и приобретённых навыков, не тест IQ или доказательство врождённого таланта.
