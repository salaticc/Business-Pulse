# Разработка и выпуск версий

## Рабочий процесс

1. Синхронизировать main без переписывания истории: `git switch main`,
   затем `git pull --ff-only`.
2. Создать ветку `feat/<topic>`, `fix/<topic>` или `docs/<topic>`.
3. Зафиксировать задачу, экспериментальную гипотезу и критерий проверки
   до просмотра нового финального TEST. Менять один понятный блок за раз.
4. Реализовать изменение, добавить необходимые проверки, обновить документацию
   и секцию Unreleased в CHANGELOG. Не переучивать правила на тестовом результате.
5. Запустить `python -m pytest -q` и нужный эксперимент. Проверять числовую
   регрессию по опубликованной синтетике можно; это не новый независимый тест.
6. Просмотреть `git diff`, добавить только относящиеся к задаче файлы;
   запустить `python -m scripts.check_repository` после `git add`.
7. Сделать содержательный commit: `feat: ...`, `fix: ...`, `docs: ...`,
   `test: ...`, `chore: ...`. Один коммит — одна логическая часть работы.
8. Отправить ветку и открыть PR в main с проблемой, результатом, проверками
   и ограничениями. Слияние — после успешного CI и просмотра изменений.

Первый перенос архивных этапов выполнен в main поверх исходного commit
владельца. Следующие продуктовые изменения идут через ветки/PR.
Автоматическая защита main настройками GitHub пока не включена;
правило workflow не следует выдавать за технический запрет прямого push.

## Данные и эксперименты

- `data/demo/` и `data/synthetic_incidents/` содержат только синтетику.
- Исходные реальные UCI-транзакции и приватные данные не хранятся в Git.
- Рабочие запуски — `outputs/`, локальная доставка/состояние — `local_state/`.
- Проверенные синтетические результаты релиза — `reports/vX.Y.Z/`.
  Не переписывать старый результат после изменения алгоритма: сохранять новый.
- Отчёт содержит input/code SHA256, версии среды, параметры и split.
  Хеши старого отчёта описывают исходный запуск; после переноса новая
  служебная программа закономерно меняет список code hashes нового запуска.
- VERSION — версия приложения. Поля `version` внутри ML/alert JSON обозначают
  протокол отчёта и не меняются только из-за добавления правил репозитория.

## Релиз

Исправление без изменения интерфейса — PATCH, новая совместимая возможность
— MINOR; несовместимость явно описывается в CHANGELOG. Для текущего 0.x
существенные изменения контракта согласовываются и сопровождаются новой MINOR.

1. В релизной ветке перенести Unreleased в новый раздел CHANGELOG и обновить VERSION.
2. При изменении ML/alert-логики выполнить заранее зафиксированный эксперимент;
   сохранить его конфигурацию, provenance и необходимые синтетические результаты.
3. Пройти тесты, проверку состава и PR; дождаться CI на финальном main commit.
4. На этом коммите создать аннотированный тег и отправить только нужный тег:

```powershell
git tag -a v0.6.1 -m "Business Pulse v0.6.1: краткое описание"
git push origin v0.6.1
```

Это пример для будущего релиза, а не указание выпускать 0.6.1 сейчас.
Опубликованные теги не переносить; исправление выпускается новым тегом.
GitHub Release с отдельными бинарными активами не требуется для работы проекта.

## CI

CI запускается при PR в main, push в main и вручную. На Windows и Linux
используется Python 3.14 и один native thread. Он устанавливает точный lockfile,
проверяет состав, запускает тесты и воспроизводит синтетический эксперимент.
Результат сравнивается с числовым эталоном v0.6.0; метаданные ОС/путей
не выдаются за побитово одинаковые между платформами.
Обновление эталона допустимо только с объяснением изменения, не ради зелёного CI.

Сторонние Actions закреплены по проверенным commit SHA. Workflow имеет
`contents: read`, не использует секретов Telegram и не выполняет deploy.
